## Purpose

Даёт пользователю явное место, где он подтверждает или отклоняет каждый планировочный артефакт OpenSpec (proposal, specs, design, tasks) до записи на диск. Гейт срабатывает в любом режиме одобрения Qwen.

## ADDED Requirements

### Requirement: Обязательное подтверждение записи артефакта
Когда агент через `write_file` или `edit` создаёт или меняет файл, который относится к планировочному артефакту change в `openspec/changes/<change>/`, расширение SHALL требовать подтверждения пользователя через нативный диалог Qwen. Это MUST выполняться во всех режимах одобрения Qwen (`default`, `auto-edit`, `auto`, `yolo`). Причина в диалоге MUST называть идентификатор артефакта и имя change.

#### Scenario: Создание proposal в режиме YOLO
- **WHEN** Qwen работает в режиме `yolo`, и агент вызывает `write_file` для `openspec/changes/add-auth/proposal.md`
- **THEN** Qwen показывает диалог подтверждения с причиной, где названы `proposal` и `add-auth`, и файл не записывается до ответа пользователя

#### Scenario: Правка spec
- **WHEN** агент вызывает `edit` для `openspec/changes/add-auth/specs/auth/login/spec.md`
- **THEN** Qwen показывает диалог подтверждения для артефакта `specs`

#### Scenario: Посторонний файл
- **WHEN** агент вызывает `write_file` для `src/index.ts`
- **THEN** расширение не вмешивается, и Qwen применяет свои обычные правила одобрения

### Requirement: Что считается артефактом
Файл SHALL считаться планировочным артефактом, если он подпадает под путь вывода (`outputPath`) одного из артефактов схемы change по данным `openspec status --json`. Если эти данные получить не удалось, MUST применяться пути схемы `spec-driven`: `proposal.md`, `design.md`, `tasks.md`, `specs/**/*.md`. Файлы в `openspec/changes/archive/` и служебные файлы change (например, `.openspec.yaml`) MUST NOT вызывать подтверждение.

#### Scenario: Пользовательская схема
- **WHEN** схема change объявляет артефакт `research` с путём `research.md`, и агент пишет `openspec/changes/x/research.md`
- **THEN** запрашивается подтверждение для артефакта `research`

#### Scenario: Статус недоступен
- **WHEN** `openspec status` для change завершился ошибкой, и агент пишет `openspec/changes/x/design.md`
- **THEN** подтверждение всё равно запрашивается

#### Scenario: Служебный файл
- **WHEN** агент правит `openspec/changes/x/.openspec.yaml`
- **THEN** подтверждение не запрашивается

### Requirement: Запись артефакта через shell
Если shell-команда агента пишет в файл артефакта change перенаправлением (`>`, `>>`), через `tee`, `cp` или `mv`, расширение SHALL требовать подтверждения так же, как для `write_file`. Команды OpenSpec CLI (`openspec …`) MUST NOT вызывать подтверждение.

#### Scenario: Перенаправление в артефакт
- **WHEN** агент выполняет `cat > openspec/changes/add-auth/tasks.md <<EOF …`
- **THEN** Qwen показывает диалог подтверждения для артефакта `tasks`

#### Scenario: Команда OpenSpec
- **WHEN** агент выполняет `openspec new change "add-auth"`
- **THEN** расширение не запрашивает подтверждение

### Requirement: Исключения и режимы гейта
Режим гейта SHALL задаваться переменной окружения `OPSX_UI_APPROVAL` или ключом `approval` в файле `.qwen/opsx-ui.json` проекта; переменная окружения важнее файла. Значения: `all` (по умолчанию) подтверждает создание и правку, `create` подтверждает только создание нового файла артефакта, `off` выключает гейт. Неизвестное значение MUST трактоваться как `all`. В фазе `apply` правки `tasks.md` (отметка задач) MUST NOT требовать подтверждения ни в каком режиме.

#### Scenario: Отметка задачи при apply
- **WHEN** фаза сессии `apply`, и агент меняет `- [ ]` на `- [x]` в `tasks.md` активного change
- **THEN** подтверждение не запрашивается

#### Scenario: Режим create
- **WHEN** режим гейта `create`, и агент правит уже существующий `proposal.md`
- **THEN** подтверждение не запрашивается

#### Scenario: Режим off
- **WHEN** режим гейта `off`
- **THEN** расширение не запрашивает подтверждение ни для каких артефактов

### Requirement: Результат решения пользователя
Когда пользователь одобрил запись и она выполнена, расширение SHALL отметить артефакт как подтверждённый в состоянии сессии. По окончании хода оно SHALL показать короткое сообщение в ленте сессии (например, `✓ opsx: design.md принят`). Когда пользователь отклонил запись, расширение SHALL отметить артефакт как отклонённый, и status line MUST показывать его отклонённым, пока артефакт не будет записан и подтверждён. Контекст расширения для агента MUST требовать после отклонённой записи не повторять её, а следовать замечаниям пользователя или спросить, что изменить.

#### Scenario: Одобрение
- **WHEN** пользователь одобрил запись `design.md`, и файл записан
- **THEN** `design` отмечен подтверждённым, а по окончании хода в ленте появилось сообщение о принятии

#### Scenario: Отклонение
- **WHEN** пользователь отклонил запись `design.md`
- **THEN** status line показывает `design` отклонённым, а файл не записан

### Requirement: Неинтерактивный режим
В неинтерактивном запуске Qwen (`qwen -p …`) подтверждение показать нельзя. Запись артефакта при включённом гейте SHALL отклоняться с причиной, где сказано, как выключить гейт для таких запусков.

#### Scenario: Headless propose
- **WHEN** Qwen запущен неинтерактивно, режим гейта `all`, и агент пишет `proposal.md`
- **THEN** запись не выполняется, а агент получает причину с указанием `OPSX_UI_APPROVAL=off`
